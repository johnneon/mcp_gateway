# MCP Gateway

Спецификация самостоятельного приложения. Документ переносится в репозиторий продукта целиком. Ссылок на чужой хост, сеть, compose и агентов здесь нет: продукт их не знает. Куда его потом поставить — решается снаружи.

Интерфейс, имена инструментов, описания инструментов и тексты ошибок MCP — на английском.

## Назначение

Шлюз хранит учётные данные приложений у себя и отдаёт клиентам MCP (Streamable HTTP). Клиент доказывает доступ bearer-токеном. Шлюз сам ходит в почту и возвращает только результат. Секрет ящика модель не получает.

Первый набор действий — почта: Gmail и Mail.ru. Список инструментов задан кодом. Клиент не добавляет инструменты и не подменяет хост.

## Стек

Один процесс на Node.js (актуальный LTS) и TypeScript.

- MCP: пакет `@modelcontextprotocol/sdk`, транспорт Streamable HTTP. Отдельного SSE-эндпоинта нет.
- Админка: React, сборка Vite, тот же процесс раздаёт статику. Своего UI-кита и отдельного фронтенд-сервиса нет.
- Данные: один файл SQLite в каталоге из окружения. Отдельная СУБД не нужна, пока процесс один.
- Секреты ящиков в базе шифруются (AES-GCM). Ключ — только из окружения. Нет ключа — процесс не стартует.

React оставлен как есть: экранов мало (вход, клиенты, ящики, журнал), а официальный MCP SDK живёт в TypeScript. Более простой связки, которую заметно легче сопровождать, нет. Next.js не используем.

## Процесс вызова

```text
MCP-клиент
  Authorization: Bearer <токен клиента>
  tools/call { name, arguments }
        │
        ▼
шлюз
  1. хеш токена → строка в таблице клиентов; нет строки или клиент выключен → отказ
  2. инструмент из фиксированного списка; аргументы проходят JSON Schema
  3. accountId есть у этого клиента; хост берётся из кода провайдера
  4. секрет ящика расшифровывается только на исходящий вызов
  5. ответ и текст ошибки чистятся от значений секретов
  6. строка журнала без тел
        │
        ▼
клиент ← текст письма или короткий результат отправки
```

Аргументы модели не содержат URL, хост и секрет. Иначе запрос можно увести на чужой сервер вместе с учётными данными.

## Граница данных

| Что | Кто видит |
| --- | --- |
| Пароль Mail.ru, refresh token Gmail, ключ шифрования | только процесс шлюза |
| Bearer клиента | оператор один раз при создании; в базе только хеш |
| Имена и схемы инструментов, подписи ящиков | модель |
| Аргументы вызова и тело ответа (тема, текст письма) | модель |
| Журнал без тел | оператор в админке |

Прячутся учётные данные, не содержимое писем. Ответ модели — это и есть данные ящика.

Значения секретов не попадают в схемы, в журнал, в ответы админки и в ошибки MCP. Если ответ провайдера случайно содержит секрет, он вырезается до отдачи клиенту.

## Клиенты

Таблица с первой версии, не один общий токен.

| Поле | Смысл |
| --- | --- |
| id | стабильный идентификатор |
| name | подпись в админке |
| token hash | хеш bearer с перцем из окружения; сам токен не хранится |
| enabled | выключенный клиент не вызывает инструменты |
| account ids | какие ящики этот клиент может передать в `accountId` |

Токен показывается один раз: при создании и при ротации. Ротация сразу гасит предыдущий. Сравнение хеша — за постоянное время. Пустой и неизвестный токен получают один и тот же отказ, без перечисления клиентов.

Bearer клиента не открывает админку. Сессия админки не вызывает MCP.

## Почта

Оба провайдера снаружи выглядят одинаково. Провайдер — свойство ящика, не аргумент модели.

Хосты зашиты в коде:

| Провайдер | Куда ходит шлюз |
| --- | --- |
| Gmail | Gmail API, хост `gmail.googleapis.com` |
| Mail.ru | IMAP `imap.mail.ru:993`, SMTP `smtp.mail.ru:465` |

Редирект на другой хост не следовать. Вложения в первой версии нет, тело письма — обычный текст.

### Инструменты

Имена и описания на английском. В `tools/list` у конкретного клиента в схеме `accountId` только разрешённые ему ящики (id и человекочитаемая подпись). Нет ни одного ящика — почтовых инструментов в списке нет.

| Инструмент | Аргументы | Ответ модели |
| --- | --- | --- |
| `list_mail_messages` | `accountId`, необязательные `query` и `limit` (потолок 20) | id, from, to, subject, date, короткий snippet |
| `get_mail_message` | `accountId`, `messageId` | то же плюс текстовое тело, обрезанное по размеру |
| `send_mail_message` | `accountId`, `to`, `subject`, `body` | id отправленного письма |

`query` у Gmail — строка поиска Gmail API. У Mail.ru — поиск IMAP по отправителю, теме или недавней почте, без произвольного протокола. Неизвестный `messageId` — обычная ошибка «не найдено», не содержимое другого ящика.

Чужой `accountId` (нет у клиента или ящик выключен) — отказ до обращения к провайдеру.

### Gmail

OAuth приложения шлюза. Оператор один раз кладёт в окружение client id и client secret своего Google Cloud OAuth-клиента. Refresh token ящика шлюз получает сам: кнопка Connect Gmail в админке, согласие Google, callback, токен в базу в зашифрованном виде.

Области: `gmail.readonly` и `gmail.send`. Access token обновляет шлюз. В MCP и в админку после сохранения он не возвращается.

### Mail.ru

Форма в админке: адрес и пароль приложения (IMAP/SMTP включены в настройках ящика). Перед сохранением шлюз проверяет вход по IMAP и SMTP. Пароль после сохранения в форме не показывается. Смена пароля — отдельное поле, пустое значит «не менять».

## Админка

Язык интерфейса — английский. Вход одним паролем администратора из окружения (в базе или в сверке — только хеш). Сессия — cookie `HttpOnly`, `SameSite=Lax`.

Экраны:

1. Sign in.
2. Clients — список, создание, токен один раз, ротация, выключение, галочки ящиков.
3. Mail accounts — Connect Gmail, форма Mail.ru, проверка соединения, отключение. Секретов на экране нет.
4. Activity — журнал: время, клиент, инструмент, ящик, успех или код ошибки, длительность. Тел нет.

## Окружение

В репозиторий попадают только имена переменных, не значения.

| Переменная | Зачем |
| --- | --- |
| адрес и порт прослушивания | HTTP админки и MCP на одном порту |
| каталог данных | файл SQLite |
| ключ шифрования | AES-GCM для секретов ящиков |
| перец токенов | хеш bearer клиентов |
| пароль администратора | вход в админку |
| Google OAuth client id и secret | согласие Gmail, не токен пользователя |

Нет обязательной переменной — процесс не стартует и пишет, какого имени не хватает, без значений.

## HTTP

| Путь | Кто |
| --- | --- |
| `GET /health` | без аутентификации; статус процесса, без каталога и секретов |
| `/mcp` | MCP, заголовок `Authorization: Bearer` |
| остальное | админка и её API, только сессия администратора |

Исходящие вызовы к почте: таймаут и предел размера ответа заданы в коде. Ошибка провайдера клиенту — короткая, на английском, без заголовков и тел, в которых мог быть секрет.

Журнал пишется и при отказе авторизации MCP (без сырого токена): время, результат «отказ», имя инструмента если оно уже разобрано.

## Сборка репозитория

Два каталога в одном репозитории, один `package.json` через workspaces:

- `server` — MCP, админ-API, почта, SQLite, миграции;
- `web` — React.

Продакшен-артефакт — один Node-процесс: API и собранный `web`. Отдельный контейнер под интерфейс не требуется. Dockerfile может появиться в репозитории продукта; привязка к чужому compose — не эта спецификация.

Порядок реализации:

1. Процесс, `/health`, миграции, вход администратора.
2. Таблица клиентов и MCP с пустым `tools/list`, пока ящиков нет.
3. Mail.ru: форма, проверка IMAP/SMTP, три инструмента.
4. Gmail: OAuth callback и те же три инструмента.
5. Журнал в админке и вырезание секретов из ответов.

## Вне скоупа

- Каталог из тысяч приложений и произвольный HTTP по шаблону из аргументов модели.
- Включение новых инструментов самим клиентом.
- Вложения, HTML-письма, черновики, календари.
- Несколько администраторов и организации.
- Выполнение кода по запросу модели.
- Публикация метрик и прокси. `GET /health` достаточен.
- Решение, на каком хосте процесс запущен. Продукт слушает адрес из окружения и на этом заканчивается.
