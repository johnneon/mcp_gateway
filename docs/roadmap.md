# Дорожная карта

Порядок, в котором продукт из `mcp-gateway-spec.md` собирается по этапам. Один этап — одно изменение OpenSpec в ветке `change/<name>` и один PR. Цикл этапа описан в `docs/workflow.md`.

- Задача для propose — «Исход» и «Входит» этапа. Источник требований — `mcp-gateway-spec.md` и `openspec/specs/`.
- Следующий этап начинается от `main` после слияния предыдущего.
- Автотест идёт на фейке, без живого сервиса. Этап, который меняет экран, ещё проходит через браузер.
- «Решить в дизайне» — вопрос, который закрывает `design.md` этапа, а не код.
- Сделанный этап лежит в `openspec/changes/archive/`.

## MVP

Оператор запускает один процесс, заводит конфигурацию и ящик Gmail в интерфейсе. MCP-клиент с bearer конфигурации читает и отправляет почту этого ящика. Пароль ящика модель не получает.

В MVP входит база без вида `proxy` и один коннектор — Gmail, вид `native`.

| № | Изменение | Исход | После |
| --- | --- | --- | --- |
| 1 | `project-skeleton` | процесс слушает два адреса из окружения | — |
| 2 | `encrypted-store` | состояние в одном зашифрованном файле | 1 |
| 3 | `mcp-port-routing` | `/health`, порты не пересекаются | 1 |
| 4 | `configurations-api` | конфигурации по HTTP | 2 |
| 5 | `mcp-endpoint` | MCP с bearer и пустым `tools/list` | 3, 4 |
| 6 | `admin-configurations-ui` | конфигурации в интерфейсе | 4 |
| 7 | `connector-contract` | коннектор — модуль в коде | 1 |
| 8 | `accounts-api` | аккаунты и выдача по HTTP | 4, 7 |
| 9 | `accounts-ui` | аккаунты и выдача в интерфейсе | 6, 8 |
| 10 | `native-tools-dispatch` | `tools/list` и `tools/call` фейкового коннектора | 5, 8 |
| 11 | `native-egress-guard` | сеть только на разрешённые адреса, секреты вырезаны | 10 |
| 12 | `connector-gmail` | чтение почты Gmail | 11 |
| 13 | `gmail-send` | отправка письма с ящика Gmail | 12 |
| 14 | `production-run` | запуск и приёмка MVP | 9, 13 |

Этапы 2 и 3 не зависят друг от друга, 7 не зависит от 2–6, 6 не зависит от 5. Параллельные ветки дают конфликты, поэтому по умолчанию этапы идут по номерам.

### 1. `project-skeleton`

Исход: процесс стартует на двух адресах из окружения. Нет обязательной переменной — не стартует и печатает имя, не значение.

- npm workspaces `server` и `web`, скрипты `typecheck`, `test`, `build`, `start`.
- Разбор окружения фиксирует имена переменных. Адрес интерфейса по умолчанию `127.0.0.1`.
- Два Express-приложения, MCP и интерфейс. Интерфейс раздаёт сборку `web` — пустую оболочку.

Проверка: старт с пропущенной переменной, соединение с обоими портами, HTML оболочки на корне интерфейса.

### 2. `encrypted-store`

Исход: всё состояние живёт в одном файле, на диске нет открытого текста.

- Файл целиком шифруется AES-GCM ключом из окружения.
- Файла нет — пустое состояние. Состояние в памяти, каждое изменение пишет файл заново: временный файл, затем переименование. Записи идут по очереди.
- Чужой ключ или битый файл — процесс не стартует, причина без ключа и без содержимого.

Решить в дизайне: формат ключа (предложение — ровно 32 байта в base64, длина проверяется при старте) и формат файла (версия, IV, тег).

Проверка: повторный старт, чтение файла с диска, старт с другим ключом, старт с битым файлом.

### 3. `mcp-port-routing`

Исход: порт MCP и порт интерфейса не отвечают на чужие запросы.

- `GET /health` на порту MCP без аутентификации: статус процесса, без каталога и секретов.
- Порт MCP отвечает только на `/health` и `/mcp`, остальное 404. Сам MCP появляется на этапе 5.
- Порт интерфейса не отвечает на `/mcp`.

Проверка: запросы к обоим портам.

### 4. `configurations-api`

Исход: оператор управляет конфигурациями по HTTP.

- Создание: случайный токен не короче 32 байт показывается один раз, в хранилище только SHA-256.
- Список без токена и хеша. Ротация сразу гасит старый токен. Выключение, удаление.
- Весь `/api`: изменение без `Content-Type: application/json` — отказ. Заголовков CORS нет.
- Галочек аккаунтов нет: аккаунтов ещё нет.

Проверка: API, запрос формой и запрос с JSON.

### 5. `mcp-endpoint`

Исход: MCP-клиент с bearer конфигурации получает пустой `tools/list`.

- Streamable HTTP на `/mcp`, отдельного SSE нет.
- Хеш токена → конфигурация, сравнение за постоянное время.
- Пустой, неизвестный и выключенный токен получают один и тот же отказ, без перечисления конфигураций.

Решить в дизайне: режим Streamable HTTP. Предложение — без сессий, токен проверяется на каждом запросе, тогда смена аккаунтов не требует уведомлений об изменении `tools/list`.

Проверка: клиент `@modelcontextprotocol/sdk` в тесте.

### 6. `admin-configurations-ui`

Исход: действия с конфигурациями доступны в английском интерфейсе. Входа нет.

- Навигация: Configurations и Connectors.
- Configurations: список, создание, токен один раз, ротация, выключение, удаление.
- Connectors: пустое состояние.

Проверка: экран через браузер, токен не виден после закрытия окна показа.

### 7. `connector-contract`

Исход: новый коннектор подключается модулем в коде. В поставке список пуст.

- Контракт: id `[a-z0-9]+`, имя, поля аккаунта (`text`, `secret`, `host`) с подписью и обязательностью, проверка соединения, разрешённые хосты, вид. В MVP реализуется только `native`.
- Поле `host` — только имя хоста, без схемы, пути и учётных данных.
- Реестр коннекторов в коде, без каталога во время работы.
- `GET /api/connectors` — описание коннекторов и полей. Экран Connectors показывает список из API.

Решить в дизайне: разрешённые адреса как пара хост и порт. Gmail нужны `imap.gmail.com:993` и `smtp.gmail.com:465`.

Проверка: фейковый коннектор в тестах.

### 8. `accounts-api`

Исход: аккаунты хранятся и выдаются конфигурациям по HTTP.

- Создание и правка сохраняются только после проверки соединения коннектора. Ошибка короткая и без секрета.
- Секретные поля в ответ API не попадают. Пустое секретное поле при правке — «не менять», новое значение снова проходит проверку.
- Проверка соединения по запросу, выключение, удаление. Удалённый аккаунт пропадает из всех конфигураций.
- Конфигурация получает список доступных аккаунтов.

Проверка: API и фейковый коннектор, секрет фикстуры не встречается ни в одном ответе.

### 9. `accounts-ui`

Исход: оператор ведёт аккаунты и выдачу в интерфейсе.

- Connectors: у каждого коннектора список аккаунтов — добавить, изменить, проверить соединение, выключить, удалить.
- Форма аккаунта строится по описанию полей, своего экрана коннектору не нужно. Секретов на экране нет.
- Configurations: галочки аккаунтов по коннекторам.

Проверка: экран через браузер, секрет фикстуры не виден на экране и в ответах API.

### 10. `native-tools-dispatch`

Исход: модель видит и вызывает инструменты фейкового коннектора только через доступные ей аккаунты.

- Имя инструмента — `<id коннектора>_<имя>`. Аргументы проходят JSON Schema.
- Шлюз добавляет обязательный параметр `account`: в схеме id и подписи только включённых аккаунтов из конфигурации.
- Коннектор без доступных аккаунтов в `tools/list` не виден.
- Чужой или выключенный `account` — отказ до обращения к коннектору.
- Обработчик получает расшифрованные значения полей аккаунта.

Решить в дизайне: как передать подписи аккаунтов в схеме `account`, чтобы их показывали клиенты.

Проверка: две конфигурации, с аккаунтом и без; счётчик вызовов фейка равен нулю при отказе.

### 11. `native-egress-guard`

Исход: коннектор не уходит за разрешённые адреса и не отдаёт секрет.

- Сетевой клиент пускает только на разрешённые адреса: HTTPS и TLS-сокеты. Сокеты нужны почте: IMAP и SMTP.
- Редирект на другой хост не выполняется. Таймаут и предел размера ответа — константы в коде.
- Значения секретов аккаунта вырезаются из ответа и из текста ошибки до отдачи клиенту.
- Ошибка клиенту короткая, на английском, без заголовков и тел.

Проверка: фейк обрывает соединение, раздувает ответ, редиректит на чужой хост, возвращает секрет.

### 12. `connector-gmail`

Исход: оператор добавляет ящик Gmail, модель читает его почту.

- Поля: адрес (`text`), пароль приложения (`secret`). Хосты `imap.gmail.com:993` и `smtp.gmail.com:465` — константы в коде.
- Проверка соединения: вход по IMAP и SMTP.
- Инструменты чтения: список, поиск и чтение письма. Точный состав — в предложении.
- Общий код IMAP и SMTP пишется отдельным модулем: Mail.ru потом отличается только хостами.

Решить в дизайне: библиотеки IMAP и SMTP при условии, что соединение идёт через сетевой клиент этапа 11.

Проверка: фейковый IMAP и SMTP сервер, без живого ящика.

Пароль приложения Gmail требует 2FA, и администратор Google Workspace может его запретить. [ПОД ВОПРОСОМ] — проверить на целевом ящике до propose.

### 13. `gmail-send`

Исход: модель отправляет письмо с ящика Gmail.

- Инструмент отправки через SMTP. Адресаты, тема и тело — аргументы модели, хост — нет.
- Отдельный этап, потому что отправка необратима, её состав и ограничения принимаются отдельно.

Проверка: фейковый SMTP сервер получает письмо, секрет не попадает в ответ.

### 14. `production-run`

Исход: MVP запускается одним процессом по инструкции.

- `npm start` запускает собранный процесс, интерфейс раздаётся тем же процессом.
- `.env.example` только с именами переменных. Инструкция: переменные, генерация ключа, подключение MCP-клиента.
- Dockerfile — по решению в предложении этапа.

Проверка: чистая сборка и старт по инструкции. Приёмку делает человек: настоящий MCP-клиент, конфигурация и тестовый ящик Gmail.

## После MVP

Порядок не задан. Каждый пункт — отдельное изменение.

### Вид `proxy`

Сторонний MCP-сервер по stdio подключается как коннектор. Тест идёт на фейковом MCP-сервере.

| Изменение | Входит | Проверка |
| --- | --- | --- |
| `proxy-runtime` | пакет с точной версией в зависимостях, без скачивания при запуске; процесс на аккаунт при первом вызове, остановка после простоя, перезапуск после падения; окружение с нуля — только сопоставленные поля аккаунта и минимум для запуска | фейк считает запуски и сообщает своё окружение |
| `proxy-tools` | наружу только разрешённые инструменты, с префиксом и параметром `account`; `account` до дочернего процесса не доходит; секрет вырезан из ответа, stderr клиенту не отдаётся | `tools/list`, аргументы в фейке, фейк возвращает секрет и пишет в stderr |

Решить в дизайне `proxy-runtime`: минимум окружения для запуска на каждой ОС (`PATH`, на Windows ещё `SYSTEMROOT`).

### Коннекторы

В изменении коннектора выбирается вид, поля аккаунта, проверка соединения и инструменты. Для `proxy` там же закрепляется пакет и список разрешённых инструментов.

| Коннектор | Учётные данные | Хосты | Проверка соединения |
| --- | --- | --- | --- |
| Mail.ru | адрес, пароль приложения (IMAP/SMTP включены в настройках ящика) | `imap.mail.ru:993`, `smtp.mail.ru:465` | вход по IMAP и SMTP |
| Jira | хост, email, API token | хост из поля аккаунта | запрос текущего пользователя |
| Notion | токен внутренней интеграции | `api.notion.com` | запрос текущего бота |

Mail.ru использует модуль IMAP и SMTP из этапа 12.

### Журнал

Оператор видит вызовы без тел, секрет в журнал не попадает. Состав полей, хранение и экран Activity решаются в его изменении.

## Вне плана

- Каталог коннекторов во время работы и произвольный HTTP из аргументов модели.
- Включение новых инструментов самим клиентом.
- Вход в интерфейс внутри продукта, несколько администраторов и организации.
- OAuth-подключение аккаунтов.
- Удалённые MCP-серверы по HTTP в виде `proxy`.
- Выполнение кода по запросу модели.
- Метрики. `GET /health` достаточен.
- Привязка к чужому хосту и compose.
