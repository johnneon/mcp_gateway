# Дальнейшие планы

Эти эпики идут после `docs/implementation.md`. Контракт коннектора уже есть: аккаунт, выдача конфигурации, `tools/list` и `tools/call`, виды `native` и `proxy`. Здесь контракт заполняется конкретными коннекторами, затем появляется журнал.

Каждый коннектор — отдельное изменение OpenSpec. В нём выбирается вид (`native` или `proxy`), поля аккаунта, проверка соединения и список инструментов. Для `proxy` там же выбирается и закрепляется пакет стороннего сервера и список разрешённых инструментов.

Порядок коннекторов не задан. Перечисленные ниже — первые из планируемых, не весь список.

## Коннекторы

| Коннектор | Учётные данные | Хосты | Проверка соединения |
| --- | --- | --- | --- |
| Gmail | адрес, пароль приложения (нужна 2FA) | `imap.gmail.com:993`, `smtp.gmail.com:465` | вход по IMAP и SMTP |
| Mail.ru | адрес, пароль приложения (IMAP/SMTP включены в настройках ящика) | `imap.mail.ru:993`, `smtp.mail.ru:465` | вход по IMAP и SMTP |
| Jira | хост, email, API token | хост из поля аккаунта | запрос текущего пользователя |
| Notion | токен внутренней интеграции | `api.notion.com` | запрос текущего бота |

Gmail и Mail.ru ходят по одному протоколу. Их общий IMAP/SMTP-код пишется один раз, коннекторы отличаются хостами. Пароль приложения Gmail может быть запрещён администратором Google Workspace. [ПОД ВОПРОСОМ] до изменения Gmail.

## Журнал

Отдельная функция после коннекторов. Исход: оператор видит вызовы без тел, секрет в журнал не попадает. Состав полей, хранение и экран Activity решаются в её изменении.

## Вне этого плана

- Каталог коннекторов во время работы и произвольный HTTP из аргументов модели.
- Включение новых инструментов самим клиентом.
- Вход в интерфейс внутри продукта, несколько администраторов и организации.
- OAuth-подключение аккаунтов.
- Удалённые MCP-серверы по HTTP в виде `proxy`.
- Выполнение кода по запросу модели.
- Метрики. `GET /health` достаточен.
- Привязка к чужому хосту и compose. Dockerfile в репозитории продукта может появиться отдельно.
