# Как ведётся разработка

Разработку ведут агенты по OpenSpec. Человек ставит задачу, принимает предложение и сливает пулл-реквест. Остальное делают агенты.

Задачи лежат на доске [Task tracker](https://github.com/users/johnneon/projects/2) как issue репозитория `johnneon/mcp_gateway`. Один issue — одно изменение, одна ветка и один PR. Правила доски — скилл `tracker`.

Каждое изменение живёт в своей ветке `change/<name>` от `main`. В `main` агенты не коммитят и не пушат. Git-правила — скилл `commits`.

## Участники

| Кто | Что делает | Чего не делает |
| --- | --- | --- |
| Человек | ставит задачу, принимает предложение, ревьюит и сливает PR | — |
| Основной агент (чат) | читает или заводит issue, уточняет задачу, запускает сабагентов, передаёт между ними артефакты и номер issue, докладывает человеку | не пишет продуктовый код сам, если есть сабагент для этого шага |
| `developer` | создаёт ветку, пишет предложение, реализует задачи, коммитит, исправляет блокеры, архивирует, пушит, открывает PR, двигает карточку issue | не принимает изменение, не сливает PR, не закрывает issue |
| `validator` | проверяет ветку в чистом контексте, пишет и коммитит отчёт | не правит продукт, тесты и артефакты изменения, не пушит, не трогает доску |

Сабагенты описаны в `.cursor/agents/`. Основной агент запускает их через Task с `subagent_type` `developer` или `validator` и передаёт имя изменения и номер issue.

## Цикл

```text
0. задача ── issue на доске ──────────────────────────────────── Backlog / Ready
  │
  ▼
1. propose ── developer ──► ветка change/<name>, артефакты, коммит ── In progress
  │
  ▼
2. review ── человек читает, правит, принимает
  │
  ▼
3. apply ── developer ──► коммит на каждую задачу
  │
  ▼
4. verify ── validator (новый контекст) ──► verification.md, коммит
  │
  ├── блокеры > 0 ──► 5. fix ── developer ──► коммиты fix: ──► снова 4
  │
  ▼ блокеров 0
6. finish ── developer ──► archive, push, PR в main с Closes #<n> ── In review
  │
  ▼
7. merge ── человек ──► GitHub закрывает issue ──────────────────── Done
```

### 0. Задача

Человек даёт ссылку на issue или номер, например `/task #7`. Основной агент читает issue по скиллу `tracker`, выводит имя изменения и обсуждает решение с человеком. Если задача пришла без issue, основной агент заводит его на доске в Backlog и даёт ссылку.

Если исход неясен, основной агент задаёт вопросы до propose. Для обсуждения без артефактов — `/opsx-explore`.

Рабочее дерево должно быть чистым. Незакоммиченные изменения, не относящиеся к задаче, — повод остановиться и спросить.

### 1. Propose

`developer` в режиме propose, скиллы `commits`, `tracker` и `openspec-propose`.

- Создаёт ветку `change/<name>` от свежего `origin/main`.
- Переводит карточку issue в In progress.
- Создаёт `openspec/changes/<name>/`: proposal, delta specs, design, tasks. В `proposal.md` под заголовком — строка `Issue: #<n>`.
- Источник — `mcp-gateway-spec.md` и текущие `openspec/specs/`.
- `npx openspec validate <name>` проходит.
- Коммит `docs:` с артефактами.
- Комментарий в issue: имя изменения, исход и то, что не входит.
- Продуктовый код не пишется. На этом шаг заканчивается.

Если человек отказывается от изменения, карточка возвращается в Backlog, issue остаётся открытым.

Основной агент показывает человеку краткое содержание, ветку и путь к артефактам.

### 2. Review

Человек читает артефакты. Правки вносит сам или просит основного агента, тогда `developer` пользуется `openspec-update-change` и коммитит правку в ту же ветку.

Apply начинается только после явного «принято» от человека. Просьба «сделай» в том же сообщении, что и задача, принятием не считается.

### 3. Apply

`developer` в режиме apply, скилл `openspec-apply-change`, в ветке `change/<name>`. По каждой задаче из `tasks.md`:

1. Код по скиллам `backend` и `frontend`.
2. Тесты в той же задаче, не после: `tests` для сценариев delta, `backend` для серверных тестов, `frontend-cover-tests` для компонентов.
3. Тесты, проверка типов, lint, format check и сборка проходят.
4. Задача отмечена в `tasks.md`.
5. Один коммит на задачу по скиллу `commits`.

`mcp-gateway-spec.md` и `openspec/specs/` не меняются. Если сценарий в delta неверен, `developer` останавливается и сообщает основному агенту. Тот возвращает вопрос человеку.

В конце `developer` докладывает, что сделано и как запустить процесс. Изменение готовым не объявляет.

### 4. Verify

Основной агент запускает `validator` новым сабагентом, без контекста разработки, в той же ветке.

- `openspec-verify-change` — задачи, требования, сценарии.
- `code-review` — diff `origin/main...HEAD` против delta, утечки секретов.
- `e2e` — интерфейс через Playwright MCP, MCP через HTTP-клиент.

Отчёт — `openspec/changes/<name>/verification.md`, форма задана в `.cursor/agents/validator.md`. `validator` коммитит только отчёт и скриншоты `e2e/`.

### 5. Fix

Блокеров больше нуля — основной агент передаёт отчёт `developer` в режиме fix. Тот исправляет только блокеры в той же ветке, коммит `fix:` на каждый блокер. Затем снова шаг 4 новым `validator`. Цикл идёт до `blockers: 0`.

Если блокер означает ошибку в самих артефактах, цикл останавливается и решение за человеком.

### 6. Finish

`blockers: 0` — основной агент запускает `developer` в режиме finish:

1. Archive — `openspec-archive-change`: delta сливается в `openspec/specs/`, изменение переезжает в `openspec/changes/archive/`. Коммит `docs:`.
2. Push — `git push -u origin change/<name>`.
3. PR в `main` через `gh pr create` по шаблону из скилла `commits`. В описании — `Closes #<n>`.
4. Карточка issue переходит в In review.

Основной агент отдаёт человеку ссылку на PR и итог отчёта.

### 7. Merge

Человек ревьюит PR и сливает его сам. Замечания к PR — снова шаг 5 в той же ветке: `developer` исправляет и коммитит, новый `validator` проверяет, `developer` пушит. Второй PR не открывается, карточка остаётся в In review.

После merge GitHub закрывает issue по `Closes #<n>`, а доска переводит закрытую карточку в Done. Агенты issue не закрывают.

### Автоматизации доски

Workflows доски дополняют шаги агентов и не должны им противоречить:

| Workflow | Статус |
| --- | --- |
| Item added to project | Backlog |
| Pull request linked to issue | In review |
| Item closed | Done |
| Auto-add to project | фильтр `is:issue` |

## Скиллы

| Скилл | Кто | Когда |
| --- | --- | --- |
| `commits` | developer, validator | ветка, коммиты, push и PR на всех шагах |
| `tracker` | основной агент, developer | issue и карточка на доске: шаги 0, 1 и 6 |
| `openspec-propose`, `openspec-update-change` | developer | шаги 1 и 2 |
| `openspec-apply-change` | developer | шаги 3 и 5 |
| `backend` | developer | код и тесты в `server/` |
| `frontend` | developer | код в `web/` |
| `frontend-cover-tests` | developer | тесты компонентов в `web/` |
| `tests` | developer | каждый сценарий delta становится тестом |
| `openspec-verify-change`, `code-review`, `e2e` | validator | шаг 4 |
| `openspec-archive-change` | developer | шаг 6 |

Скиллы `openspec-*` генерирует CLI, руками их не правят. Проектные скиллы лежат в `.cursor/skills/` без префикса `openspec-`.

## Готово к finish

- все пункты `tasks.md` отмечены и закоммичены;
- `npx openspec validate <name>` проходит;
- сценарии delta покрыты автотестами, тесты проходят;
- e2e по затронутым сценариям прошёл;
- `openspec/changes/<name>/verification.md` закоммичен и в нём `blockers: 0`.

Сессия, которая писала код, изменение принятым не объявляет. Принятие — это merge PR человеком.
